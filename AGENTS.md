# BotsEverywhere

Open source team management tool for bots. It runs on this computer. Template mode and showcase mode have no logins. [botseverywhere.ai](https://botseverywhere.ai) is the read-only showcase.

Two modes (`src/mode.ts`):

- **template** (default). Local org files under `orgs/`. `npm run dev` starts the site and the file writer. The UI writes through that writer (`canEditFiles` is true only in dev template mode).
- **showcase**. `VITE_APP_MODE=showcase`. Read-only sample organizations, directory, and docs. The public site.

`sqlite` in the same file is a separate share-link API. Leave it off. The writer (`server/src/index.ts`) listens only when `MODE` is `template` (the default). `MODE=showcase` does not start an API.

## Stack and commands

Vite, React 19, TypeScript. The local writer is Node in `server/src/template-server.ts` and binds to `127.0.0.1` only. `server/src/app.ts` is the sqlite app, not the file writer.

```bash
npm install
npm run dev
```

`scripts/dev-all.ts` prints the URLs it bound. Defaults are the site at `http://127.0.0.1:5199` and the writer at `http://127.0.0.1:8787` (`scripts/dev-ports.ts`). If a port is taken, the writer walks forward from 8787 (up to 20 tries) and the site takes the next free port from 5199, skipping the writer port. `PORT` and `WEB_PORT` override those starts.

```bash
npm test          # node --import tsx --test server/test/*.test.ts
npm run build     # validate orgs, directory, and mocks; generate bots; tsc; vite build; tsc -p server
```

`npm test` does not filter on extra arguments. To run one file: `node --import tsx --test server/test/<file>.test.ts`.

VS Code marks the imports in `server/test/*.ts` as errors (TS5097, a path may not end in `.ts`; TS2591, no Node types) because no tsconfig includes `server/test/`. That is the editor only: `node --import tsx` does not type-check, and the tests run.

Two things to know before reading a red run as a regression. `server/test/org-node-layout.test.ts` needs Chrome at `/usr/bin/google-chrome` (or `CHROME_PATH`) and is skipped without it, so a Windows run shows 1 skipped. `npm run build` regenerates `src/generated/bots.ts` from `bots/*.md`; on 23 October 2026 a build left it unchanged. If a build changes it, run `git checkout -- src/generated/bots.ts` unless the change is about that file. The writer is started by `tsx` without a watcher, so a change under `server/src/` needs `npm run dev` restarted. A failed hot reload (Vite error overlay) leaves the old module in the tab until a hard reload.

## Org files

`orgs/<slug>/` (writer root `ORGS_DIR`, default `orgs`):

The folder name is the organization's ID and never changes. A new org or a template copy gets `org-` and 8 characters from `ID_CHARS` in `server/src/project.ts`, no look-alikes (`uniqueOrgId` in `server/src/template-server.ts`). The name lives in `org.md` alone, so renaming an organization only rewrites `org.md`. Never derive a folder from the name and never move an org folder: the Connector briefs each bot with absolute paths to its seat, process, and log files, and the bot keeps them in its memory. Older folders named after a name (`your-company`) are IDs too and stay as they are.

- `org.md` — YAML frontmatter (`name`, `description`, `industry`, `size`, `people`, `bots`, optional `fallbackProcess`, `mark`, `markColor`) then purpose text, `## Departments`, `## People`, `## Chart` (`- <seat>` or `- <seat>: <reportsTo>`). A file with `## Chart` is a markdown org.
- `seats/<slug>.md` — frontmatter: `title`, `department`, `reportsTo`, optional `alsoReportsTo` (a JSON list of seat slugs, written right after `reportsTo`: extra managers, drawn as dotted lines; a bad entry, the seat itself, and its main manager are dropped on read, and a loop through main and extra lines is refused, `managerLoop` in `server/src/org-files.ts`), `addToGrokBotUrl`, `status` (`active` or `retired`), `kind` (`human`, `bot`, or `system`), `role`, optional `description`, `personId`, `hiredAt`, `retiredAt`, `directoryId`. Bots may also carry `instructions` (the prompt, line breaks JSON-encoded), `skills` (JSON list of `{ name, description }`), and `publicUrl` (https share link), written beside `routines` by `metricLines` so both seat formats keep them. Body sections: `## Owns`, `## May`, `## Needs approval`, `## Done when`.
- `work-chart.md` — triggers, workstreams, steps, handoffs, checkpoints.
- `processes/<slug>.md` — frontmatter `name`, `trigger` (`schedule`, `event`, or `manual`), `schedule` or `source`, `description`, `doneWhen`, optional `next`. Body: `## Steps` as `- <seat> | <action>`, then `## Notes`.
- `log/YYYY-MM-DD.md` — daily run log. Header `# Run log YYYY-MM-DD`. One line, six fields split on ` | `:

  `- HH:MM | bot | process | step | done|failed|skipped|waiting|running | note or -`

  Bad lines are skipped. The header is not a line. A bot logs each chat as one line with `chat` as the process (`CHAT_PROCESS` in `server/src/bot-metrics.ts`).
- `log/<event>.md` — one activity event (hire, fire, edit, work, approval, exception) with YAML frontmatter (`id`, `type`, `actorSeatId`, `actorType`, `timestamp`) and the summary as the body. A `YYYY-MM-DD.md` name is a run log, not an event.
- `grok/snapshot.json` — written by the writer from the Connector's `orgs/grok-data.json` (`runConnectorCycle` in `server/src/connector-cycle.ts`); with no `grok-data.json`, an older Connector writes it itself. One object: `syncedAt`, `bots` (the bots-file format), `processes` (the processes-file format). A broken snapshot is reported in the Sync drawer and never breaks the org.
- `grok/requests.json` — written by the app (**Create in Grok Bot**, below). One object, key `requests`. The Connector reads it and never edits it. A `deletes` list from an earlier version is ignored and dropped on the next write.

Beside the org folders, `orgs/` holds the project files, all gitignored (names in `server/src/connector-files.ts` and `server/src/project.ts`):

- `project.json` — `{ "id", "syncMinutes", "removeCopies" }`. The app owns it. `id` is this copy's 4-character id (`server/src/project.ts`); a missing or bad file gets a fresh id. `removeCopies` lists other copies whose blocks the owner asked to remove (`POST /api/connector/remove-copy`); every write keeps it.
- `CONNECTOR.md` — the Connector's rules, written by the app (`connectorGuide` in `server/src/connector-prompt.ts`) when the writer starts and when the interval changes. The Connector reads it on every run.
- `grok-data.json` — written by the Connector on every run: what it sees in Grok Bot. Validated strictly (`parseGrokData` in `server/src/grok-data.ts`); a bad one changes no file and shows in the Sync drawer.
- `connector-todo.json` — written by the app: what the Connector still has to do, each item with a key and the exact text to send (`computeTodo` in `server/src/connector-todo.ts`). `connector-results.json` — written by the Connector: one result per key, never removed.
- `grok-unassigned.json` — written by the app from `grok-data.json`: bots in no organization. When it exists it wins over `connector.json`'s list. `connector-backups/<bot>/` — each bot's instructions before the Connector changed them.
- `connector.json` — written by the Connector last on every run: `syncedAt`, `syncMinutes` (the interval it runs at), `unassigned` (bots in Grok Bot that belong to no org), and `apps` (apps connected to the Grok Bot account: `name` and `status`, `connected` or `needsAuth`; nothing else is kept). Its file time is the heartbeat. Each bot in a snapshot may list `apps`, the names of the connected apps it uses; they land on the seat (`apps` frontmatter) on every Connector run like the numbers, a report without them clears them, and `recordConnectorRun` logs `apps` lines (an app connected, needs sign-in, or left) and `bot-apps` lines (a bot now uses or no longer uses an app). Apps show on bot cards, in Profile, in the Performance Apps column, and in Logs (`src/org/bot-apps.ts`).
- `connector-log.json` — the writer's memory of what it already logged about each Connector run (`server/src/connector-log.ts`).

The writer watches `log/`, `processes/`, `grok/`, `profiles/` (each bot's own profile file, `server/src/profile-files.ts`; sent as `event: grok`), `seats/*.md`, and `org.md` and pushes SSE on `GET /api/orgs/<slug>/live` (`event: log`, `event: processes`, `event: grok`, `event: org`). A change to `orgs/connector.json`, `orgs/project.json`, `orgs/grok-data.json`, or `orgs/connector-results.json` sends `grok` to every open org, runs the cycle, and two seconds later the writer runs `recordConnectorRun`. Any other change in an org folder except its log runs the cycle two seconds later.

## Bots JSON

Import and export use `botseverywhere-bots.json` (`docs/bots-file.md`, parser `server/src/bots-file.ts`). Import fills an empty organization once: when it has a bot other than the Connector (`importLocked`), Connect bots shows `IMPORT_LOCKED` with Add a seat, Bot directory, and Export bots file instead of the two options, and `POST /api/orgs/<slug>/bots-file` answers 409. The preview is `POST /api/orgs/<slug>/bots-file/preview` (`previewBotsFile`): it runs the same import on a throwaway copy of the organization folder, reading the other organizations where they are, and answers with each bot as it would be saved (`reportsTo`, `alsoReportsTo`, `worksIn`, notes). Connect bots shows that, never the managers the file names, so a greyed bot shows the managers it has where it works. Sync and adopting bots in no organization still add bots. One object, key `bots`. Each bot: `name` (required), optional `grokBotUrl`, `reportsTo` (defaults to You; a name that is not a seat here places the bot under You with a note), `alsoReportsTo` (names; one that is not a seat here is left out with a note), `owns`, `may`, `needsApproval`, `doneWhen`, and performance fields `createdAt`, `lastActive`, `runs30d`, `tasksDone30d`, `routines` (`name`, `schedule` or `trigger`, optional `lastRun`), `status` (`active`, `paused`, or `retired`). A file may carry `section`, the Grok Bot sidebar section; the parser ignores it for now. Option 1 on Connect bots has no file: **Import from the Connector** (`POST /api/orgs/<slug>/connector-import`), disabled with a note until the Connector's first run, and the panel says what it does. Option 2 pairs `public/bots-file-template.json` (a `readme`, an `instructions` list that is `BOTS_FILE_PROMPT` line for line, a `fields` guide, all skipped by the import, and three Northwind examples) with `botsFilePrompt` (`src/content/bots-file-prompt.ts`), a prompt for any AI that interviews the owner and confirms the bots before it writes the file. The Option 2 prompt shown on Connect bots names the time zone of the computer showing it (`botsFilePrompt(localTimeZone())`). Unknown numbers and dates are dropped with a note. `status` is stored as seat frontmatter `botStatus`, not seat `status`. Prompt rule: if a value is unknown, leave the field out. Never estimate or invent numbers.

Option 4 imports an organization that already exists from `botseverywhere-organization.json` (`docs/organization-file.md`, parser `server/src/org-file.ts`, import `importOrgFile` in `server/src/template-server.ts`, `POST /api/orgs/<slug>/org-file`). It pairs `public/organization-file-template.json` (a `readme`, an `instructions` list that is `ORG_FILE_PROMPT` from `src/content/org-file-prompt.ts` line for line, a `fields` guide, and a Northwind example) with a prompt whose blanks the owner fills in: name, websites, social media, description, people, and which one is you. Keys: `organization` (`description`, `purpose`, `industry`, `size`; the organization keeps its name), `departments`, `people` (`name` required, `title`, `department`, `reportsTo` as one name or a list with the main one first, `owns`, `email`, `phone`, `location`, `about`), and `you`. It writes departments, People in `org.md`, one human seat per person, and the chart; the person in `you` becomes the `you` seat. Extra managers become the seat's `alsoReportsTo`; one that would make a loop is left out. Several people can be at the top. It runs only while the organization has just You and the Connector (`orgImportLocked`, `ORG_IMPORT_LOCKED`, 409). People do not count for `importLocked`, so Options 1 and 2 stay open after it. Seat and department file names drop accents (`plainSlug`).

## Connector

One Connector serves every org in a copy of BotsEverywhere (spec `docs/superpowers/specs/2026-10-18-project-connector-design.md`). The bot name is `Connector - BotsEverywhere (<id>)`, with `<id>` from `orgs/project.json`. Its run-log bot field is `Connector`. The prompt pasted once is `connectorBootstrapPrompt` in `server/src/connector-prompt.ts`; it points the Connector at `orgs/CONNECTOR.md`, which holds its rules, so a new interval or rule needs no new paste. The UI shows the prompt on the Connect bots tab (`src/components/ConnectGrok.tsx`) and in Docs (`#connect-grok`); `CONNECTOR.md` is not shown there, only listed under Files the Connector uses. `connectorPrompt` is the older prompt, kept for reference.

The app decides; the Connector moves data and acts. On each run the Connector writes `orgs/grok-data.json` and then `orgs/connector.json`. From that dump and the org files, the writer writes each org's snapshot, the unassigned list, backups, and `connector-todo.json`; the Connector carries out each item exactly and records `connector-results.json`. An item that fails twice, or a routine a bot does not confirm after two asks, is stuck and shows in the Sync drawer. Managers, team, skills, and logging rules reach a bot as one block per organization at the end of its instructions (`server/src/bot-blocks.ts`); the owner's text outside the blocks is never changed, and another copy's blocks are removed only when the owner asks. Creating bots, saving skills, and asking for routines still follow `grok/requests.json`. The Connector never edits the app's files and never reads outside `orgs/`. Grok Bot gives it no tool to delete a bot. A bot it creates goes into the Grok Bot sidebar section named like the organization in `org.md` (capital letters ignored), or the request's `section`, which the app does not write yet; with no such section it creates the bot without one and notes `noSection` on its sync line. It cannot create a section or move a bot that already exists, so the person makes the sections and drags existing bots once.

**Runs every** on Connect bots saves `syncMinutes` (15 minutes to 7 days) to `orgs/project.json` (`PUT /api/project/sync-minutes`), rewrites `CONNECTOR.md`, and rewrites the schedule of the Connector's own process in every org (`syncConnectorProcesses`). The Connector changes its schedule on its next run; Connect bots and the header dropdown warn until `connector.json` reports the same `syncMinutes`. Three intervals without a run means the Connector stopped (`staleMinutes` in `server/src/connector-timing.ts`); Grok Bot does not run it on an exact clock. The header badge (`GrokStatusBadge.tsx`) and the connection bar (`ConnectionBar.tsx`) read the light `GET /api/connector`, which reads only `project.json` and `connector.json`; the org page loads the full sync plan apart. Both open on the last state this browser tab saw (`src/live/connector-memory.ts`), then ask again; see Speed. The badge shows the last run time under the state and opens a dropdown with Runs every, Last sync, and Next sync.

The Connector's status comes from one file: the modified time of `orgs/connector.json` is its last run (`readConnector` in `server/src/project.ts`, `connectorState` in `sync-copy.ts`), and the date inside it is used only when the file time cannot be read. No file means Not connected; a file that is not JSON means Error; more than three intervals since the last run means Stopped. Step 1 on Connect bots shows that file as **Status file**: `connector.json`, "When the Connector last ran", and its last run time, from the same reading as the Status line (`connectorStatusFile` in `src/components/file-guide-copy.ts`). A run that fails before writing `connector.json` is invisible to the app, and saving that file by hand looks like a run.

**Sync with Grok Bot** on the org tab row (`src/components/SyncDrawer.tsx`) previews the merge (`GET /api/orgs/<slug>/sync`) and applies it (`POST .../sync/apply`; `POST .../sync/preview` still takes a pasted file, but the drawer no longer offers one: the app writes every snapshot from the Connector's dump). The plan is pure, in `server/src/grok-sync.ts`. The app owns `reportsTo`, step assignments, and filled card sections; Grok Bot owns the link, routines, run numbers, and whether a bot exists. A sync never deletes a seat: a bot missing from Grok Bot is tagged `grokSync: missing`. Seat frontmatter carries `grokSync`, `grokSyncedAt`, `grokMissingSince`, and `grokDeletedAt`. Bots in `connector.json` `unassigned` show in every org's Sync drawer under **In Grok Bot, no organization**; Sync adds the ticked ones to this org as seats marked New. `PUT /api/orgs/<slug>/seats/<seat>/manager` moves a seat and refuses cycles; with `alsoReportsTo` it also sets the extra managers (the seat drawer's Also reports to). Under **Going to Grok Bot** the drawer also shows what the Connector could not do (`connectorState` in `server/src/connector-cycle.ts`): stuck items with their reason, items on their second try, items it has not acted on for more than two runs (shown as still working through them when it recorded results since, `actedSince`), a dump it could not read, and other copies' blocks, under **Old instructions from other copies of BotsEverywhere**, with **Remove old instructions** (it rewrites only those blocks, bot by bot; bots are never deleted). A copy whose Connector is not in the dump is marked (`connectorGone`), and two or more such copies get **Remove all old instructions** (`oldCopies` in `sync-copy.ts`). The setup text shows only until the Connector is connected, and the bot limit only past 50.

## One bot, one organization

Spec `docs/superpowers/specs/2026-10-29-one-bot-one-organization-design.md`. A bot works for one organization. The exceptions, in every organization: the Connector (any name starting `Connector - BotsEverywhere`) and the main bot, saved by Grok Bot id as `mainBot` in `orgs/project.json` (`readMainBot` and `writeMainBot` in `server/src/project.ts`). Bots are told apart by the id in their link (`botKey`), never by name.

- **Import from the Connector** (Connect bots, Option 1, once the Connector has reported): `POST /api/orgs/<slug>/connector-import` (`importFromConnector`) imports every bot in `grok-data.json` (`rowsFromDump`), each under the manager its own text names, and the Connector from the dump's `self`, else from another organization's Connector seat, else without a link. `CONNECTOR.md` asks for `reportsTo`, `alsoReportsTo` (from each bot's own text, outside every BotsEverywhere block), `skills` (the names turned on for each bot, as Grok Bot shows them; `skillsFor` in `grok-data.ts` gives each the library's description, and a dump without the field falls back to library skills the bot's own text names), and `self`; a dump without them still reads. The main bot and the Connector never lock the import (`importLocked(seats, mainBot)`).
- **Greyed seats.** Every bots-file import (`importBotsFile`) brings a bot active in another organization in greyed: its link in `elsewhereUrl`, `grokBotUrl` empty, no numbers (`isGreyed`). A greyed seat goes under the managers it has in the organization it works for (`HomeManagers` from `botsInOtherOrgs`, matched by Grok Bot id), main and extra, when they are here, greyed or not; else by its own text. A seat that works here never reports to a greyed one: it waits under You with `waitsFor`, and moves under it when that bot starts working here, unless the owner moved it since. `grokSeats` keeps greyed seats out of blocks, snapshots, Sync, the Connector log, and the account count; Create in Grok Bot refuses them. `POST /api/orgs/<slug>/seats/existing` (Add existing bot) still refuses such a bot with 409 and offers Add anyway; its buttons on Connect bots and the org chart are off for now, and `ExistingBotDrawer` stays.
- **The greyed seat's panel** (`src/components/GreyedSeatBox.tsx`): **Move it here** (`moveBotHere`, `POST .../seats/<seat>/move-here`: retired in every other organization with `movedTo`, its reports there go under its manager there, Delete in Grok Bot is not offered for it), **Rename and publish in Grok Bot** (`publishCopy`, `POST .../publish` with `{ name }`: a new name, then a Create in Grok Bot request; the original's name is refused), **Remove** (`removeGreyedSeat`, `DELETE .../seats/<seat>`), and, while no main bot is saved, **It's my main bot** (`markMainBot`, `POST .../main-bot`). `GET .../sync` carries `elsewhere` (greyed seat to organization names, read live) and `mainBot`. While no main bot is saved (`mainBot` is `''`) and the organization has a greyed bot, the Org Chart asks **Which bot is your main bot?** above the chart (`src/components/MainBotBar.tsx`; choices from `mainBotChoices` in `sync-copy.ts`, the greyed bot most seats report to first). **It's my main bot** posts the same `.../main-bot`; **Not now** hides it for that organization in this browser (`localStorage`).

## Speed

The writer answers one request at a time, and its reads are synchronous (`readFileSync`, `readdirSync`). A slow request delays every other one, the Connector status included, and that is what kept **Checking the Connector…** on screen. Measured numbers are in `docs/STATUS.md`. Keep these:

- To learn whether the writer answers, ask `GET /api/connector` (a few ms), never a whole org. The org page's 5 s writer check does.
- The org page sends `GET /api/connector` first and the sync plan only after it answers (`loadSync` in `src/pages/Workspace.tsx`).
- Every org tab mounts a new `Workspace` (`key={`${slug}-${tab}`}` in `src/App.tsx`), so state kept in it starts over on each tab switch. The connection bar and the header badge share the last Connector state in session storage (`src/live/connector-memory.ts`, key `be:grok-status`) and show it at once.
- A request that asks about every org reads each org once. `syncStatus` hands one `orgReader` (`server/src/template-server.ts`) to `projectInfo`, `projectBots`, `grokAccount`, and `retiredActiveElsewhere`; before, one sync read the requested org four times and every other org three times. Nothing is cached between requests: the plan depends on every org, `connector.json`, `requests.json`, and files the watcher does not report, so a cache could serve a stale plan.
- `src/org/load.ts` bundles every file under `orgs/` into the front end with eager `import.meta.glob`. In dev, the Vite plugin `scripts/quiet-org-files.ts` keeps a change under `orgs/` from sending a hot update; the file is only marked stale for the next page load. `<org>/org.md` stays live because it names the orgs, and an `orgs/` that is a link counts by its real folder too. Without it, one Connector run sent about a hundred hot updates into six pages, and each re-ran their requests. The bundled copy feeds only the first paint, the **Open your org** shortcut, and the start of the org list, so after a seat or log change those catch up on a page reload. Org pages read the writer.

## Org chart

`src/components/OrgChart.tsx`. The viewport keeps its own height (`.org-viewport` is `flex: 0 0 auto`) and scrolls natively. A mouse drag on the background pans under pointer capture; the plain wheel zooms around the pointer; the segmented control (−, readout, +, Fit) and pinch zoom too. The resize observer watches the border box, so scrollbars appearing or vanishing never re-fit. Zoom helpers live in `src/components/org-zoom.ts`.

On an org of your own (`grokStates={editable}`), a bot card shows its Grok Bot state from `src/components/sync-copy.ts`: green bar and **In Grok Bot** when the last sync saw it or when it carries a `grokBotUrl` link; **New in Grok Bot** when a sync created it; dashed and muted **Not in Grok Bot** when a snapshot lacked it (`grokSync: missing`); muted **Not synced yet** when nothing is known. Templates and samples stay plain. The seat drawer has a **Reports to** select (`PUT /api/orgs/<slug>/seats/<seat>/manager`), which refuses the seat itself and any cycle.

The seat drawer's tabs: **Seat card** is the bot's place in the organization (Reports to, Owns, May, Needs approval, Done when). **Profile** is how the bot works. On an org of your own it is `src/components/BotProfile.tsx`, chosen by `origin` (`profileParts` in `src/components/bot-profile-copy.ts`): a directory bot (`directoryId`) shows its category, summary, and prompt, editable after hiring, and an unedited prompt is not stored; a bot imported from Grok Bot (`source: existing`) says "This seat is not in the directory. It was imported from Grok Bot."; a bot added with Add a seat gets **Instructions for Grok Bot**, skills and routines to fill in, and **Add to Grok Bot**. Skills and routines edit like the Grok Bot Graph panel: a skill is a name and what it does, with a remove button, until the Connector's reading shows it saved in the library and named on the bot's "Skills to use" line (`grokSkills` on the routine board, `skillsInBlock` in `server/src/routine-board.ts`; a skill the bot reports using that the reading does not name is shown locked too, `knownInGrok` in `src/org/bot-skills.ts`); then it is locked (**In Grok Bot**, `keptSkills` in `bot-profile-copy.ts`) and removed only there, as a bot is; a routine is a card (Name, Description, Starts, a cron Schedule with Presets and the plain-words line from `cronText`, or an Event rule, Time zone, Active) closed with Done; `draftRoutines` keeps only what fits its start. A bot with a `publicUrl` shows **Get this bot**. Saves go to `PUT /api/orgs/<slug>/seats/<seat>/profile` (`updateSeatProfile`), which never touches the card or the manager. Every bot of your own takes skills and routines. Templates keep the old Profile plus read-only skills and routines. The app never edits a public link; the share-link paste box is gone.

**Create in Grok Bot** sends the Profile: `prompt` is `instructions`, else the directory prompt, else empty (the Connector then builds it from the card), and the request carries `skills` and `routines`.
